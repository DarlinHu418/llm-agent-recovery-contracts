**首先，幂等键究竟解决了哪一层问题？**

在目标服务正确实现去重、键仍在有效期内等前提下，幂等键解决的是：

> **已经确定这些请求属于同一次操作之后，怎样避免产生重复副作用。**

它本身不负责判断“这次新生成的调用，究竟是不是之前那次操作”。但是，**这个判断问题也并非 Agent 时代才出现**：AWS 已明确讨论过“相同参数可能代表两次合法操作”，以及“同一个请求ID携带不同参数”的情况。因此，不能把“业务意图与请求参数不同”当成我们的原创发现。[AWS 工程说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

以发送通知为例：

| 情形 | 正确处理 |
|---|---|
| 通知已经发送，回执丢失，Agent 尝试恢复 | 继承原操作，复用原键 |
| 换一个 Agent 接手同一项发送任务 | 继承原操作，复用原键 |
| 用户明确要求“把同一条通知再发一次” | 建立新的授权操作，使用新键 |
| 原通知结果未明，用户要求修改内容 | 先处理原操作的不确定状态，再按业务规则决定后续动作 |

这张表说明了研究对象，但**表中的规则本身仍然不构成创新**。如果 Workflow 已经保存并正确传递了操作关联，传统方法就能处理这些情况。

已有研究对我们的原始构想覆盖得比“普通工具重试”更深：

- **LIMBO，2026年预印本**：已经记录 Agent 重试时更换键的错误，并明确提出由运行时为同一意图固定键。因此，“发现 Agent 会换键”“禁止模型修改键”均不能独立作为创新。[论文正文](https://arxiv.org/html/2609.29095v1)
- **CapLease，2026年预印本**：本次补检发现，上一版报告遗漏。它把规范化动作、用户确认事件和执行预算绑定到持久授权状态，覆盖重规划、重试、委派和崩溃恢复；还与具有同等状态的 Server Ledger 比较。这与我们提出的“授权事件＋操作记录＋稳定键”高度重合。[论文正文](https://arxiv.org/html/2608.01710v1)

CapLease 还测试了语义规范化，所以我们也不能简单宣称“别人只比较键，我们识别语义”。以上是论文作者报告的设计和结果，本次没有独立复现实验。

**因此，上一版报告中的方案应被理解为候选研究方案，不能被理解为已经确立的新方法。漏掉 CapLease 会影响新颖性判断，这一点需要纠正。**

**那么，仍然值得研究的具体增量是什么？**

我建议把重心收紧到：

> **在持久账本和目标幂等机制已经完善的条件下，上下文压缩与重规划是否仍会导致新计划中的动作错误关联到既有操作？怎样以较低成本恢复这种关联，同时避免阻止合法的再次执行？**

这里需要区分两件事：

- **后台操作记录是否还存在**：由数据库和 Workflow 保障。
- **Agent 当前提出的动作能否正确关联到那条记录**：需要通过执行轨迹、授权来源和业务规则判断。

账本存在，并不自动意味着关联正确；但关联错误也可能通过简单的结构化引用传递完全解决。**研究必须允许这个结果出现，不能预设必须使用语义模型。**

具体可争取的贡献有三个层次：

| 候选贡献 | 必须提供的证据 | 创新强度判断 |
|---|---|---|
| 建立针对压缩、重规划的身份关联评测 | 同时包含“应继承旧操作”和“应建立新操作”的成对任务；与已有基准明确区分 | 较适合课程研究 |
| 找出身份关联失效的具体条件 | 控制工具契约和后台账本，只改变压缩内容、引用传递或计划结构 | 有价值的实证贡献 |
| 提出轻量关联恢复机制 | 相比完整账本按需查询、结构化引用等强基线，在安全性相当时降低查询、token或人工澄清成本 | 有条件的方法增量 |

“增加几个字段”本身不新；**证明哪些信息不可丢、哪些信息可以按需取回，以及保护它们能否产生可重复的收益**，才可能形成研究贡献。

这里还有一个容易忽略的反例：完整账本可以保存在数据库里，按需查询，并不需要全部塞进上下文。因此，不能通过“我们的短记录”对比“把完整历史全部输入模型”，就宣称轻量化成功。

**怎样用一个小实验判断这个题目是否真的成立？**

先只做一个通知工具，暂时不扩展复杂多智能体系统。设置两类必须同时通过的任务：

1. **同一次授权的恢复**：发送成功但回执丢失，随后压缩上下文并重规划，正确结果仍应只有一次发送。
2. **新的合法授权**：用户明确要求再次发送相同内容，正确结果应允许第二次发送。

比较四种机制：

- 模型根据对话自行恢复。
- Workflow 持久保存操作ID，并在计划变更时传递结构化引用。
- 完整账本与按需查询。
- 拟提出的轻量记录与关联恢复策略。

实验同时统计重复发送、合法操作被误拦截、任务完成率、查询与token成本，以及澄清次数。评分依据独立保存的授权事件与实际发送记录，不能只看键是否相同。

关键判据是：

> **如果“持久操作ID＋结构化引用＋按需查询”已经低成本解决所有测试，我们就没有必要再设计一套语义归并机制。**

这种情况下，课程报告仍可以形成一项边界清楚的实证研究：哪些失败来自错误的工程实现，哪些才需要 Agent 理解；但不能再宣称提出了新的恢复机制。

就目前证据而言，**这个题目可以继续做，最有希望的是“聚焦场景的实证评测与轻量工程增量”，尚不足以宣称基础机制创新。** 我建议把第一阶段研究问题固定为：

> **上下文压缩后，基于持久账本的操作引用传递，能否同时避免重复执行和合法重复操作的误拦截；更复杂的语义恢复是否带来额外收益？**

这也最符合你的立场：通过实验确定哪些事情交给确定性 Workflow 就足够，哪些信息缺失需要补查或澄清，而不是先假定 Agent 应当自主解决一切。

## 025 助手 2026-11-10T09:45:57.220Z commentary

本次使用 `nature-academic-search` 和 `nature-writing`，核对“授权次数”与“操作身份”的关系，并把允许重规划的折中机制具体化。


## 026 助手 2026-11-10T09:46:57.869Z final_answer

**如果用户确实要求执行两次，系统就不能因为文本相同而只执行一次；那属于误去重，会造成任务遗漏。确实存在折中机制：让 Agent 修改执行计划，同时由 Workflow 独立保存和维护已批准操作的身份。**

这里要分别记录：**执行什么、执行几次、当前是哪一次的尝试。**

例如，“给张三发送两次‘会议取消’”，两次发送的文本、接收人甚至所有参数都可以完全相同，但它们仍是两个业务操作。AWS 也明确指出，相同参数可能代表用户希望创建两个相同资源，因此不能仅凭参数相同认定为重复请求。[AWS 工程说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

系统可以把它们合并成一个批量调度任务，但必须保留“两次发送”的效果。**可以合并处理过程，不能把应有的两次效果压缩成一次。**

还有一个必须明确的区别：

- 用户说“发送两次”：完成条件是两次都成功。
- 用户说“最多可以发送两次”：两次是授权上限，并不意味着必须执行两次。

因此，“没有超过授权次数”只证明没有超额执行，不证明任务已经完成。

**折中方案的核心，是让计划节点引用操作，而不是让计划节点定义操作身份。**

可以把系统分成两部分：

| 对象 | 保存什么 | 谁能修改 |
|---|---|---|
| 执行计划 | 步骤、顺序、负责人、检索与验证方式 | Agent 可在约束内重规划 |
| 已批准操作记录 | 授权来源、操作内容、次数、操作ID、执行状态 | Workflow 按确定规则维护 |

对于“发送两次”，Workflow 可以创建：

| 授权 | 操作实例 | 内容 | 幂等键 |
|---|---|---|---|
| A：发送两次 | O1：第一次发送 | 会议取消 | K1 |
| A：发送两次 | O2：第二次发送 | 会议取消 | K2 |

如果用户先后分别授权两次，也可以记录成两个授权事件，各自对应一个操作。**两次执行不要求必须有两次确认，但必须有足以覆盖两次执行的可信授权。**

随后，Agent 的计划可以从：

> 查询联系人 → 执行 O1 → 执行 O2 → 汇总

改成：

> 委派联系人查询 → 执行 O1 → 核查结果 → 将 O2 交给另一 Agent → 汇总

步骤名称、节点数量和执行者都改变了，但 O1、O2 保持不变。接手的 Agent 获得的是既有操作的引用，不是重新创建同一操作的权力。

如果 O1 超时，恢复过程仍然使用 O1 和 K1；如果执行第二次发送，则使用 O2 和 K2。**重试次数可以增加，已批准的操作次数不会因此增加。**

这种“授权实例、执行预算、稳定键与持久状态相结合”的基本思路已有研究支持。CapLease 预印本就区分了授权身份与执行者、会话等执行上下文，并支持一次授权下的多个执行名额。因此，基础框架本身不能作为我们的原创贡献。[CapLease 正文](https://arxiv.org/html/2608.01710v1)

**Agent 的自由应该停在哪里？**

可以把允许的计划修改明确列出来：

| 计划修改 | 是否可自主进行 | 身份处理 |
|---|---|---|
| 重命名步骤、增加查询和校验步骤 | 可以，受工具权限约束 | 仍引用原操作 |
| 更换负责的 Agent | 可以，需通过委派规则 | 转移执行责任，保留原身份 |
| 调整执行顺序 | 依赖业务先后约束 | 不产生新操作 |
| 失败后再次尝试 | 按恢复规则进行 | 复用原操作和原键 |
| 修改接收人、金额、通知正文等效果字段 | 需检查原授权是否允许 | 不能悄悄覆盖旧操作 |
| 增加一次发送、扣款或创建资源 | 必须有额外授权额度 | 创建新的操作实例 |

这里不必要求每次参数变化都再次询问用户。例如，用户可能已经授权“在预算内选择配送方式”。Workflow 可以允许这种范围内的选择。但这些可变范围必须来自既有授权或业务规则，不能由 Agent 在重规划时自行扩大。

尤其需要禁止一种行为：

> **旧操作结果未知时，Agent 把它从计划中删除，再创建一个内容相同的新操作，借此绕开恢复流程。**

删除计划节点不能删除后台操作记录，也不能消除已经发出的请求。已发生的副作用更不会随着计划改写而撤销。

**这个机制仍有一个无法靠技术凭空消除的边界：授权含义不明确。**

例如，第一次发送结果未知，用户说“再来一次”。这可能表示：

- 继续完成刚才那次；
- 无论刚才是否成功，都额外发送一次。

如果可信上下文不足，两种解释都成立，系统就需要补查或澄清。不能让模型生成一个新ID，就把歧义变成了新的授权。反过来，如果用户已经明确说“额外再发送一次，即使上一条已经成功”，系统也不能因内容相同而拦截。

这为你的课题提供了一个更具体的研究对象：

> **当 Agent 修改计划时，能否通过持久操作引用和受约束的计划修改规则，保持已批准操作的身份与次数，同时允许合法的新操作？**

实验必须同时检查三件事：**同一操作不会因重规划被重复创建，明确要求的第二次操作不会被吞掉，结果未知的旧操作不会因计划变化而失去追踪。** 只有三者同时成立，才能说明机制在支持重规划的同时守住了授权边界。

## 029 助手 2026-11-10T09:57:24.172Z final_answer

**研究仍可能有价值，但新机制未必有价值。如果简单 Workflow 加稳定 ID 已经低成本解决问题，就应该采用它，删除没有收益的新模块。** 研究的价值不能靠保住预先设计的方案来证明。

关键是区分两个目标：

- **研究目标**：查清重规划为什么导致身份漂移，以及需要什么保障。
- **方案目标**：证明我们设计的机制比已有方法更好。

第一个目标可以成功，而第二个目标被实验否定。这是合理的研究结果，但必须如实调整贡献表述。

需要先确认，“已经足够”究竟意味着什么。强基线应同时做到：

1. 同一次操作跨重试、压缩和交接保持身份，不产生重复副作用。
2. 用户明确授权的第二次相同操作能够执行，不被误合并。
3. 结果未知的操作能够继续恢复，不靠全部拒绝来获得安全。
4. 存储、查询、token、延迟和人工澄清成本可以接受。

**如果它只是不重复，却经常漏执行或要求人工处理，就还没有解决完整问题。** 反过来，如果这四项都满足，就不能为了显示新机制有效，故意削弱基线。

可以按实验结果直接决定方案去留：

| 实验结果 | 合理结论 |
|---|---|
| 新机制更安全，且没有明显损害完成率 | 有机制改进的证据 |
| 安全性和完成率相当，但成本更低 | 有工程优化价值 |
| 只在某类真实约束下更好 | 保留为条件性方案，明确适用范围 |
| 各项表现相当，但实现更复杂 | 删除新机制 |
| 重复更少，但误拦截、遗漏更多 | 不能宣称可靠性提升，需要评价取舍 |

其中，“相当”需要足够样本和不确定性分析支持，不能把“没有发现显著差异”直接解释为“两者一样好”。

即使最后删除新机制，这项研究仍可能形成三类有效结论：

**第一，定位真正的故障原因。**  
例如，实验可能支持：在所测场景中，问题主要来自运行时没有持久保存和传递操作引用，而不是模型必须具备更强的语义推理能力。这个判断需要通过控制变量验证，不能仅凭基线表现好就推断。

**第二，确定必要保障，而不是增加系统复杂度。**  
通过逐项去除稳定ID、授权次数记录、未决状态和交接引用，查明哪些条件不可缺少，哪些模块没有额外收益。这里应区分安全性与恢复能力：某个字段可能不影响防重复，却影响任务能否继续完成。

**第三，提供能同时发现重复和误去重的评测。**  
如果评测只有“同一任务重试”，稳定ID胜出并不意外。加入“相同文本、合法执行两次”和“旧操作未决时修改计划”等对照，才能说明简单机制究竟覆盖了哪些边界。评测本身也需要与已有工作比较，不能仅因整理成测试集就宣称创新。

不过，需要坦率地区分成果层级：**一项严谨的边界验证可以成为很好的课程研究；它是否足以成为有新颖性的论文，还取决于相对已有研究增加了什么证据。** 仅重复证明“稳定幂等键有效”，贡献通常有限。

因此，你的课题更适合把主问题写成：

> **在允许 Agent 重规划的条件下，维持操作身份与授权次数需要哪些最小运行时保障，语义恢复机制是否提供额外收益？**

这样，实验发现复杂机制有效，是结果；发现简单 Workflow 已经足够，也是结果。最终应交付的是**有证据支持的最小方案及其适用边界**，而不是必须保留下来的“新机制”。

## 032 助手 2026-11-10T10:00:52.770Z final_answer

**会。单个模拟通知服务只能支持有边界的机制结论，不能直接证明真实生产系统中的发生率。要把身份漂移归因于自主重规划，还必须提供对照和干预证据；“注入超时后出现重复发送”远远不够。**

这里需要分别回答两个问题：环境是否真实地实现了故障，以及故障之后究竟是谁改变了操作身份。

**先让故障脚本只制造不确定性，不直接制造身份漂移。**

例如，故障注入器可以让请求没有到达、提交后丢失回执，或者延迟提交。但它不能修改操作ID、删除账本、生成新授权，也不能向 Agent 提示“请创建新操作重新发送”。

应当保持这样的职责边界：

| 组件 | 可以决定什么 | 不能决定什么 |
|---|---|---|
| 故障注入器 | 请求或响应是否丢失、提交延迟 | 新操作ID、恢复计划、用户授权 |
| Agent | 后续查询、等待、重试和计划调整 | 后台真实提交结果 |
| 执行适配层 | 按公开规则映射并发送请求 | 暗中换键、凭空补充授权 |
| 独立评分器 | 依据授权记录与实际效果判定错误 | 根据 Agent 自称成功就判定成功 |

LIMBO 已采用服务边界故障注入、隐藏效果账本和观察等价的故障对照：请求未执行与执行后丢回执，可以呈现相同的超时响应。这个设计值得借鉴，而不是把超时写成“触发重复发送”的脚本。[LIMBO 正文](https://arxiv.org/html/2609.29095v1)

在运行模型之前，还要用确定性客户端验证环境：

- 同键重试确实只提交一次。
- 新键确实可能产生第二次效果。
- 两次合法授权不会被评分器误判成重复。
- 丢失回执不会删除已经产生的效果。
- 即使客户端停止，预先安排的延迟提交仍会发生。

这些检查证明模拟器没有偷偷替某种方案提供保护，也没有强迫所有客户端失败。

**其次，必须观察到“身份在哪里改变”，不能仅从重复结果倒推。**

每次调用至少记录四个位置：

> Agent 原始工具请求 → 适配层实际请求 → 服务接收记录 → 最终效果账本

同时保存可观察的计划版本、节点引用和交接记录。这些是正常系统输出，不需要索取模型的内部思维过程。

一个有解释力的失败轨迹可以是：

1. 用户只授权发送一次，系统建立操作 O1。
2. Agent 发出 O1，服务提交，但回执丢失。
3. Agent 修改计划，新建一个发送节点。
4. 新节点没有关联 O1，而是提出或触发建立 O2。
5. O2 使用新键，导致第二次发送。

但必须继续核对第4步：

- 如果 Agent 已正确引用 O1，适配层却自动换键，属于运行时问题。
- 如果计划没有变化，只是普通重试时换键，属于恢复中的身份错误，不能直接称为重规划导致。
- 如果用户新增了授权，建立 O2 可能完全正确。
- 如果只是计划节点改名，操作引用仍是 O1，就没有身份漂移。

**计划变化、身份漂移和重复副作用是三个不同事件，必须分别测量。**

**第三，用对照实验检验重规划的作用，而不是只展示失败案例。**

建议从同一个执行检查点分支，比较下面四组：

| 条件 | 无故障 | 相同的超时故障 |
|---|---|---|
| 固定计划结构，保留查询和恢复能力 | A | B |
| 允许 Agent 修改计划结构 | C | D |

任务、授权、初始计划、工具文档和服务契约保持一致。故障按预先确定的业务调用位置触发，避免不同组因为多调用了一个查询工具，就撞上不同的故障。

这个对照可以检验：

> **开放计划修改能力，是否增加了身份关联错误；这种变化是否在故障下更明显。**

但要诚实说明：它估计的是“允许重规划这一执行策略”的影响。固定计划也可能改变调用次数、查询策略和完成率，所以不能把所有差异都解释为重规划本身。

也不能只挑出“实际发生重规划”的轨迹来比较：困难任务本来就更容易同时出现重规划和错误。主分析应包含各组全部任务；重规划子集用于补充描述。

**还需要一个更直接的干预：保持重规划自由，只固定操作引用。**

在允许重规划的条件下，再比较：

- Agent 可重新建立操作关联。
- Workflow 保持既有操作引用，并验证授权和参数；Agent 仍可修改步骤与负责人。

如果两组都发生了计划修改，但第二组身份漂移减少，且合法第二次操作和任务完成率没有受损，就支持以下解释：

> 风险来自重规划过程中操作关联被重新建立，而不是修改计划必然不安全。

如果只是因为第二组拦截了所有后续执行，重复减少就不构成有效证据。还应检验另一种结果：固定引用后重复依然存在，那就需要检查传输重投递、服务去重契约或适配层错误，而不能继续归因于身份漂移。

上下文压缩、任务交接应随后分别加入，避免第一轮就同时改变所有因素。

**最后，怎样降低“只对人为环境成立”的风险？**

不需要立即接入真实短信或支付，但至少应增加两种独立性：

1. **实现独立性。** 除内存模拟器外，用真实 HTTP 请求、持久数据库和响应丢弃代理复现关键轨迹。这样能检查问题是否依赖玩具函数的特殊实现。
2. **任务独立性。** 在未参与方案开发的新任务模板上测试，并迁移到一个独立实现的工单创建服务。单纯把通知服务改名为工单服务，不算有效迁移。

主实验中的用户授权最好由人工编写并固定。否则，模拟用户临时补充授权也会改变正确答案。ToolSandbox 的研究已经表明，LLM 用户模拟器本身可能产生幻觉和指令遵循错误，需要单独校验。[ToolSandbox 正文](https://arxiv.org/html/2408.04682v2)

最终结论应分强弱表达：

- **仅观察到失败轨迹：** 该环境中存在身份漂移的可能路径。
- **加入受控对照与身份固定干预：** 在所测条件下，证据支持重规划中的身份关联变化参与造成错误。
- **跨实现、任务和模型重复出现：** 该机制具有一定迁移性。
- **没有生产数据：** 仍不能报告真实系统中的普遍发生率。

你的研究不必证明“故障与错误无关”。故障可以是触发条件。真正需要证明的是：**故障脚本没有预写身份错误；错误出现在可定位的决策或映射环节，而且对该环节的干预能够改变结果。**

| 最终获得的结果 | 能否支撑创新 |
|---|---|
| Agent 重规划后生成了新ID，产生重复效果 | 通常只是已知现象的复现 |

| 发现已有方案在其宣称适用的条件下仍有未识别失效路径 | 可能形成新发现，需要核查与复现 |
| 在相同保障和公平基线下，取得明确的成本或完成率收益 | 可能形成增量创新 |
| 提供已有评测遗漏、且会改变方案优劣判断的测试维度 | 可能形成评测贡献 |

关键不是“我们有没有换一个场景”，而是：

1. **已有强方案正确实现之后，究竟还剩什么错误？**

2. **剩余错误为什么不是已有问题的另一种表现？**  
   需要指出与既有机制、假设或评价对象的具体差别，而不只是换术语、换服务。

3. **解决它是否需要新增机制？**

**值得保留的最小问题，是“业务效果不变，但调用划分变了”。**

例如，用户批准：

> 给甲、乙各发送一次通知。

Agent 最初计划调用：

```text
send_batch([甲, 乙], key=K)
```

发生超时后，它可能重新规划为：

```text
send_one(甲, key=K1)
send_one(乙, key=K2)
```

目标没有改变，但请求结构和去重范围发生了变化。如果原批次已经完成了甲的发送，拆分后的请求可能再次发送给甲。

直接沿用旧键也未必可行：如果服务绑定键与原请求参数，修改 payload 会产生冲突。Resend 官方文档明确规定，同键不同 payload 会冲突，其批次接口也使用请求级幂等键。[幂等键文档](https://resend.com/docs/dashboard/emails/idempotency-keys)、[批次接口文档](https://resend.com/docs/api-reference/emails/send-batch-emails)

这里不能推断 Resend 具有某种部分提交行为。**部分提交、同键续作和逐项去重，必须分别作为明确的服务契约测试。**

LIMBO 已研究部分批次，并在键充分性的讨论中包含“中断批次在同键下续作”的条件。但“恢复原请求”和“把原请求改成多个新请求”，不是同一种恢复操作。[LIMBO 正文](https://arxiv.org/html/2609.29095v1)

这使问题可以收紧为：

> **当 Agent 拆分或合并待恢复的调用时，哪些计划修改仍处于既有幂等保障范围内，哪些修改必须等待旧效果澄清？**

逐项幂等本身仍是已有工程方法。候选增量在于系统评价以下三者的交互：

- Agent 改变了什么调用粒度；
- 服务在哪个粒度执行去重；
- 用户究竟批准了哪些效果、各几次。

|---|---:|---:|---|
| 两个操作分别使用不同键 | 2份 | 1次 | 正确 |
| 按内容保存回执并抑制后续调用 | 1份 | 0次 | 少执行一次 |

| 恢复方式 | 只有请求级去重 | 支持跨批逐项去重 |
|---|---|---|
| 原键、原参数恢复原批次 | 正确 | 正确 |
| 拆成新键的单项请求 | 已完成项重复 | 正确 |
| 原键但修改批次参数 | 参数冲突、任务未完成 | 同样冲突 |

两组各运行6条确定性轨迹，全部断言通过。**它们没有调用模型，不证明 Agent 自然会选择这些恢复方式，也不衡量生产发生率。** 它们证明了评分迁移问题和契约差异确实可以被执行、观察和复核。

**据此，我建议采用以下研究定位。**

题目进一步收紧为：

> **《面向批量通知重规划的操作粒度变化与身份保持评测》**

保留原题也可以，把上述内容作为唯一主要场景，暂时不同时扩展压缩、多智能体并发和跨供应商恢复。

最小研究贡献可以分成两层：

1. **评测贡献：** 构建成对任务，在授权不变时改变调用划分，在调用内容相同时改变合法执行次数，检查现有恢复机制的错误类型和比较结果是否改变。
2. **条件性的机制贡献：** 用少量契约规则检查计划修改，允许安全的拆分，保留不安全的未决效果，检验是否比完整账本方案具有更低成本或更好的安全完成表现。

轻量机制不需要新模型。它可以维护逐效果实例，而不是只维护批次：

- 已确认完成的效果，返回回执；
- 已证明未执行的效果，允许重新分批；
- 结果未决的效果，按有效原请求恢复，或依赖明确的跨批逐项去重；
- 新授权要求额外一份时，建立新效果实例。

这些规则的组成件都有先例。**只有实验显示额外收益，才能把它写成机制改进；否则保留评测贡献，采用已有 Workflow。**

**从严格审稿角度，仍必须过三关。**

- **新颖性审查：** 不能把上述代码边界夸大成全领域缺陷。需要展示具体工作负载相对已有套件增加了什么，以及它是否改变实际比较或设计选择。
- **技术审查：** 不能只数最终总量。“同一授权超额一次、另一授权漏一次”可能抵消为正确总数，正式评分必须检查逐授权归属。
- **实用性审查：** 必须保留“稳定批次ID恢复”“从开始就使用逐效果ID”“持久账本按需查询”这些强基线。不得通过削弱 Workflow 证明新模块有用。

正式实验还要允许 Agent 自行选择是否拆批，保存原始调用与适配后请求；手工编排的拆批只能验证机制，不能证明自主重规划的因果作用。

**我的立项建议是：推进这个小型评测研究，暂不宣称提出新恢复协议。** 它已有可复核反例、清晰的近似工作差别和轻量实现路径。若强基线在这些任务上低成本全部通过，就删除新门控；若新评测连错误解释或机制比较都没有改变，则进一步收缩为工件复核。这样可以推进研究，同时避免再次把成熟工程原则包装成创新。

据此，当前判断应当是：

| 行为主张 | 当前证据判断 |
|---|---|
| 失败后改变工具或执行路径 | 有研究案例支持 |
| 失败后重新组合并行调用 | 有真实系统轨迹报告支持，尚未独立复现 |
| 一个业务批量请求失败后，自主改成多个小请求 | 有直接使用报告，但缺少强轨迹证据 |
| 失败后自主合并原本分开的业务请求 | 本次未找到足够直接的证据 |
| 上述行为发生在副作用未决之后，并导致重复效果 | 尚未核实完整证据链 |

这里还有一个重要区别：**同一轮发出多个独立工具调用，不等于调用一个 `send_batch` 接口。** 前者改变并行调度，后者改变请求参数及去重边界。Claude Code 的并行调用案例不能直接替代批量通知API的证据。

**这意味着，我们现在首先要验证的是行为是否存在，而不是继续完善防护机制。**

上一轮的确定性诊断只证明：

> 如果恢复过程中改变调用划分，某些契约下可能失去原有保护。

它没有证明：

> 未受诱导的真实 Agent 会选择这种恢复方式。

因此，批次重规划目前适合进入**探索性先导实验**，还不足以直接确立为论文的核心现象。

最小验证可以这样做：

- 同时提供批量和单条工具，说明真实参数与契约，不提示“失败后拆批”。
- 让 Agent 自己选择初始调用方式；不能先强制批量，再把后续行为称为完全自主。
- 分别设置无故障、执行前失败、提交后丢回执；故障脚本只改变服务结果，不改变计划或参数。
- 保存模型原始工具调用和实际发送请求，确认变化来自模型，而非 SDK 自动重试或自动切片。
- 分别报告初始批量使用率、失败后的拆分率、重新组合率，以及其中涉及未决效果的比例。

如果只能在提示“尝试小批次”之后观察到拆分，那测到的是**受提示的恢复能力**；如果模型自然拆分的是只读查询，也不能直接外推到不可逆写操作；如果几乎没有自然拆批，就应收缩这一切口。

**目前最稳妥的结论是：真实 Agent 会调整失败后的执行组织，拆批有现实线索；但“批量副作用未决后的自主拆批或合批”仍是需要先验证的研究假设。** 这项存在性验证应成为下一阶段的首要实验门槛，避免围绕一个尚未确认的行为设计整套机制。

## 049 助手 2026-11-10T12:07:42.105Z final_answer

**调用粒度变化的影响，取决于工具端究竟“按什么单位去重”，以及重复请求是“返回旧结果”还是“继续完成未执行部分”。** 同样一次拆批，在不同契约下，可能安全完成，也可能重复执行、参数冲突，或没有重复却漏掉合法操作。

因此，不能只把工具分成“支持幂等”和“不支持幂等”。

设一个明确的分析场景：

> 用户要求给甲、乙、丙各发送一次通知。原批次执行了甲、乙，随后超时，丙尚未执行。Agent 准备改变调用划分。

这里的真实状态仅供分析；运行中的 Agent 未必知道。这也是一个**非原子批次的假设场景，不代表具体厂商的内部行为**。

**不同契约会产生以下差别。**

| 工具端契约 | 改变调用粒度后的主要风险 | 对遗漏和完成的影响 |
|---|---|---|
| 无去重保障 | 拆成新请求重发，已完成项可能重复 | 容易补齐遗漏，但完成可能伴随重复 |
| 请求级键，绑定完整参数 | 子批次沿用旧键可能参数冲突；使用新键通常不继承旧请求保护 | 拒绝修改可避免额外执行，却可能阻塞恢复 |
| 请求级键，只重放已记录结果 | 原样重试可能一直返回旧的部分结果 | 可以不重复，但不保证补齐未完成项 |
| 请求级键，支持中断后续作 | 原键原参数恢复可以只完成剩余部分；拆成新请求可能绕开进度记录 | 原请求恢复可能已足够，不必允许拆批 |
| 跨批次、跨相关接口的逐效果实例去重 | 保留原逐项身份时，拆批、合批通常仍能抑制重复 | 更有利于独立恢复剩余项，但仍依赖重试、可用性和正确参数 |
| 按内容去重 | 相同内容可能被折成一个效果 | 能抑制某些重复，也可能吞掉合法的第二次执行 |

这些是契约层面的条件分析，不能直接转换成某个模型的实验发生率。

Resend 就明确规定：同键不同 payload 会返回冲突，其批量接口的键按 API 请求使用。因此，“保留了旧键”并不意味着可以任意修改批次参数。[幂等键规则](https://resend.com/docs/dashboard/emails/idempotency-keys)、[批量接口](https://resend.com/docs/api-reference/emails/send-batch-emails)

**最容易混淆的是：防止重复，不等于恢复完成。**

仍用上述三人通知场景，下面是几种可能的结算结果：

| 恢复行为及前提 | 最终发送次数：甲、乙、丙 | 重复 | 遗漏 |
|---|---|---:|---:|
| 新键拆批，三人全部重发，无跨批逐项去重 | 2、2、1 | 2次 | 0次 |
| 原样重试，但工具只返回旧部分结果、不续作 | 1、1、0 | 0次 | 1次 |
| 原键原参数重试，工具支持中断续作 | 1、1、1 | 0次 | 0次 |
| 拆批，且从首次提交起就有跨批逐项去重 | 1、1、1 | 0次 | 0次 |

这是推演，不是模型实验数据。它说明：

- 只统计重复，会偏爱停止或过度拦截的策略。
- 只检查“每个人是否至少收到一次”，会把第一行也算作完成。
- 同时要求不重复、不遗漏，才能区分有效恢复与带副作用的完成。

LIMBO 对同键恢复的充分性讨论，也明确包含“中断批次在同键下继续执行”的条件。**不能把这个续作条件省略，然后宣称任何幂等键都能恢复部分批次。** [LIMBO 正文](https://arxiv.org/html/2609.29095v1)

**逐项去重允许更大的重规划自由，但有几个严格前提。**

第一，逐项身份必须从第一次提交起就被工具端认可。原批次只携带一个批次键，超时后才给单条请求补上新逐项键，无法追溯性地保护已经发生的发送。

第二，身份必须代表一次合法发生实例。例如用户要求给甲发送两份相同通知，应有两个实例：

```text
甲的第一份：E1
甲的第二份：E2
```

重试 E1 不能再产生一份；执行 E2 则必须允许。若两者都使用“接收人＋通知内容”的哈希，就可能错误合并。

第三，保护范围必须连续。逐项键只在批量接口有效，而单条接口使用另一个命名空间时，批量转单条仍可能失去保护。同样，换供应商、换账户或超过保留期，都需要重新检查契约。

第四，目标端的去重记录与效果提交必须正确协调。本地记录“已经派发”不能替代目标端去重，也不能证明消息已经发送。

逐项处理已有成熟工程先例。AWS 的部分批次指南将失败项重试和逐项幂等分别处理，说明这两种能力需要配合使用。[AWS 官方指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/lambda-event-filtering-partial-batch-responses-for-sqs/best-practices-partial-batch-responses.html)

**合批与拆批遵循同一个判断原则：是否重新覆盖了已经完成或仍可能完成的效果。**

例如，把两个失败批次合成一个新批次时：

- 已确认完成的项，应附回执，不应再次发送；
- 有权威证据证明未执行的项，可以进入新的批次；
- 结果未决的项，不能仅因查询暂时为空就当作未执行；
- 若旧请求仍可能提交，只有覆盖这些项的跨批去重等保障，才能支持安全重组。

所以，调用粒度变化本身并不必然危险。危险来自**新请求覆盖了旧请求的效果，却没有继承相同的保护范围**。

**对研究而言，应把三项结果分别测量。**

1. **超额执行**：超过对应授权允许次数的实际效果。
2. **合法操作遗漏**：应完成的效果，在规定结算条件下没有完成。
3. **安全完成率**：应完成项全部完成，同时没有超额或越权效果。

运行时仍不确定的操作，还要单列“未决”，不能直接当作遗漏或成功。另外，“最多允许两次”和“必须执行两次”的完成条件不同，评分器必须区分。

这会形成一个更具体、可检验的研究假设：

> **当调用划分改变而逐效果保护范围不能保持时，积极恢复更容易增加重复，保守拦截更容易增加未决或遗漏；如果保护范围能够连续保持，重规划可能补齐任务而不增加重复。**

应当用实验检验这个交互，而不是预设“拆批有害”或“逐项方案必然最优”。如果工具已经支持低成本的原批次续作，**稳定批次ID加原请求恢复可能就是最合适的方案**。

**会改变，而且我们已有一个局部、可复核的例子。但“按授权效果实例计数”本身不是足够的创新。更值得独立研究的是：现有恢复策略的优劣判断，是否受到了调用划分方式的干扰？**

我建议把课题从“构建更多恢复任务”转向**审查失败恢复评价的测量有效性**。核心问题可以写成：

> **当用户授权和实际效果保持不变时，恢复策略的评分是否会随请求、计划节点或任务的划分而改变？如何区分这种评分伪差异，与策略确实改善了授权履行的真实收益？**

这个问题研究的是评价方法是否可信，测试集只是验证它的材料。

**为什么仅改成“效果实例计数”还不够？**

CapLease 已定义授权实例、执行预算和效果计数；RetryBench 已区分恢复许可、最终效果与恢复完成；AuthorizationPairs 已研究授权变化和合法操作被误拒绝。因此，不能把“按授权计账”“同时统计重复和遗漏”或“授权对照”作为首创。[CapLease](https://arxiv.org/html/2608.01710v1)、[RetryBench](https://arxiv.org/html/2610.15884v4)、[AuthorizationPairs](https://arxiv.org/html/2610.16838v1)

可以争取的增量，是进一步研究：**不同策略采用不同执行结构时，现有评价单位能否支持公平比较。**

例如，一个策略把恢复组织成一个父任务，另一个策略为每次尝试建立新节点。如果评分器把这些节点直接当作业务操作，那么策略可能仅凭改变节点划分，就减少“重复数”，而没有减少任何实际副作用。

**本次我新增运行了一个冻结轨迹诊断。**

保留同一份授权和同一条实际效果历史，只在评分适配层改变分组方式。结果如下：

| 实际效果历史：用户要求两份 | 按父任务分组的重复数 | 按效果节点分组 | 按尝试节点分组 | 授权效果评价：超额、遗漏 |
|---|---:|---:|---:|---|
| 正确完成两份 | 1 | 0 | 0 | 0、0 |
| 只完成一份 | 0 | 0 | 0 | 0、1 |
| 第一份执行两次，第二份一次 | 2 | 1 | 0 | 1、0 |

三条冻结历史、三种表征，共9次评分检查及授权敏感性检查，均通过断言。

这里有一个严格的适用范围：**原 IdempotencyBench 的 `task_id` 有固定业务含义；本诊断刻意检查把任意计划分组映射到它之后的迁移问题，不证明原任务集有错，也没有重算真实模型排名。** 它证明的是一种具体的评价适配风险。

这个例子揭示了两种不同的问题：

- 过度抑制合法操作，可以获得零重复，却没有完成任务。
- 把真正重复的执行分散到多个“新任务”，可能让重复从评分中消失。

如果评价能够受这种划分影响，那么“某恢复策略更可靠”就可能只是评分单位与它的实现方式更相容。

**独立评测问题应当同时包含“不变性”和“敏感性”。**

| 要求 | 什么应该固定或改变 | 评价应有的表现 |
|---|---|---|
| **表征不变性** | 授权、真实效果及相关时序固定，只改变日志分组、节点名称等表征 | 恢复正确性保持不变 |
| **授权敏感性** | 内容和效果数量固定，改变有效授权要求 | 正确性应随之改变 |
| **证据充分性** | 缺少可信的提交或授权关联证据 | 标为不可判定，不能默认安全 |

例如，同样发送两份通知：

- 只允许一份：存在超额执行。
- 明确要求两份：正确。
- 明确要求三份：存在遗漏。
- 最多允许三份：不能据此判定遗漏。

**效果实例是逻辑评价单位，不必等于一次API调用，也不必强制每份效果对应一次用户确认。** 如果业务允许多个等价授权互换使用，评分器也应允许合法匹配；不能人为指定一个任意 slot，再把其他合法绑定判错。

这些原则本身不是新数学理论。潜在贡献在于把它们变成可执行的恢复评价检查，并证明它们是否影响了真实策略选择。

**最重要的方法区别，是把两种实验分开。**

**第一种是“只改变评价表征”。**  
冻结已有执行轨迹，不重新运行 Agent。保持授权与真实效果不变，只改变评分输入如何分组。如果正确性分数变化，就能定位评价对表征的依赖，不会与模型随机性、工具故障混淆。

**第二种是“真正改变调用方式”。**  
让 Agent 使用批量、单条或不同恢复计划重新执行。实际效果可能改变，这时分数当然可以改变。

不能要求“真正拆批后产生了重复”的执行仍获得相同分数。我们要求不变的是**相同业务事实的不同记录方式**，不是所有不同执行都必须等价。

这也构成与一般变形测试的差别：AgentMorph 等工作已改变用户表述或工具表面来检查模型行为；这里首先改变的是**评价表征，审查评价器本身**。[AgentMorph 公开规则](https://huggingface.co/datasets/Anonymous2535k/agentmorph-bugs-v0.1)

**什么结果才足以形成独立贡献？**

不能仅展示一次排名翻转。至少需要建立下面的证据链：

1. **识别测量依赖。** 在正确说明适用范围后，证明某种评价或适配方式会把相同业务事实评价成不同结果。
2. **解释机制。** 指出问题来自任务划分、内容去重、策略可控的标识或分母，而不是笼统说“旧指标粗糙”。
3. **提供可执行修正。** 建立独立于策略的授权—效果规范记录，并给出哪些证据足以判定、哪些只能保留未知。
4. **检验实际影响。** 在真实轨迹和正确 Workflow 强基线上，检查修正是否改变错误解释、策略间的支配关系或实际选型。

这里不必强求一个总排名。更稳妥的是分别比较超额执行、遗漏、安全完成、延迟和成本。如果一个策略只是重复更少、遗漏更多，应报告取舍；不能临时选择惩罚权重制造赢家。

**研究审查中的三个关键门槛是：**

- **新颖性：** 按授权实例计数已有先例，贡献应落在评价有效性的系统审计及其证据。
- **技术有效性：** 真值不能来自 Agent 自报的操作ID；没有可信关联时，不能补造归属。
- **实用意义：** 如果正确对接后的现有评价器都满足这些要求，且策略比较没有变化，那么成果只是适配器一致性检查，不足以宣称领域性的评价缺陷。

因此，我更推荐的题目是：

> **《Agent失败恢复策略排序的测量有效性：授权效果实例与调用划分不变性》**

它比“扩充批量通知恢复测试集”更明确：**研究策略优势究竟来自履行授权，还是来自评价对实现结构的依赖。** 这是一项可独立定义、可执行审计、也能够被否证的评测研究；目前已完成的是其确定性诊断，真实策略比较仍待实验建立。

## 073 助手 2026-11-10T15:22:52.368Z final_answer

**拆批或重组批次本身不会必然破坏幂等。关键在于：工具把“同一次操作”识别为整条请求，还是每个业务效果；重规划后是否仍落在原来的去重范围内。**

还要区分三种结果：**重复副作用被挡住、恢复请求被拒绝、任务最终完成**。幂等保障通常只承诺第一项，并不自动保证后两项。

**1．什么时候仍然有效？**

若要允许 Agent 自由重组批次，同时保持逐项防重，通常需要以下条件：

| 条件 | 具体要求 |
|---|---|
| 效果身份独立于批次 | A 无论放在哪个批次，都携带同一个 `effect_id` |
| 身份在首次提交前确定 | 第一次批量调用就已经把逐项身份传给实际执行方，不能超时后才补 |
| 工具确实按项去重 | 后端按每个效果的身份识别重试，而非只检查整个请求的键 |
| 参数与授权绑定不变 | 相同 ID 仍指向相同收件人、金额、内容等；合法的新操作使用不同 ID |
| 去重状态仍然有效 | 未超过保留期限，未切换到另一个账户、区域、端点或不共享账本的执行方 |
| 执行与防重状态可靠衔接 | 并发重试、崩溃和迟到请求不能绕过防重检查 |
| 重组没有改变业务约束 | 原本要求原子完成或有先后依赖的操作，不能随意拆开、并行执行 |

这里的 `effect_id` 是**获批效果实例的身份**。一个授权若明确要求执行两次，就应有两个实例身份，不能简单地把授权 ID 当成唯一效果 ID。

在这些条件下，下面两种安排可以保留相同的防重能力：

```text
原安排：[A(id=a), B(id=b), C(id=c)]

新安排：[A(id=a)] + [C(id=c), B(id=b)]
```

即使原请求仍在执行，后续请求再次包含 A，执行端也应识别为同一实例。AWS 的工程说明特别强调，幂等令牌记录与业务状态变更必须可靠地形成原子操作，避免“效果已发生，令牌却没有记录”的窗口。[AWS 幂等 API 设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

**但逐项防重不保证顺序正确，也不保证整批原子性。** A、B 各执行一次，仍可能因顺序错误或只完成一半而违反业务要求。

**2．什么时候会失去保障，或者无法继续恢复？**

假设原请求是：

```text
send_batch([A, B], key=K)
```

A、B 内容不同，各只授权执行一次。客户端收到超时，不知道实际提交情况。

| 原有契约与恢复动作 | 结果 |
|---|---|
| 整请求幂等，保持原请求体和 K 重试 | 在契约有效期内，原防重保障仍适用 |
| 整请求幂等，拆成 `[A]`，继续使用 K | 可能因请求体不同而被拒绝；防重没有坏，但恢复受阻 |
| 整请求幂等，拆成 `[A]`、`[B]`，分别使用新键 | 原 K 不再覆盖新请求；已执行的项可能再次执行 |
| 弱实现只看 K、不校验请求体 | 可能把整批旧回执当成子批结果，错误跳过尚未完成的项 |
| 原本逐项幂等，但重规划为 A 生成了新 ID | 同一个业务效果被识别为新操作，可能重复 |
| ID 不变，但记录过期或去重作用域改变 | 同一个字符串也可能被当成新请求 |

这些边界存在于真实产品中。例如，Resend 的批量邮件接口使用整批幂等键；官方文档规定同键不同请求体返回 `409`，并说明键保留 24 小时。**由此可推断，拆批后复用整批键不能自动获得逐邮件恢复能力；换新键则不能依靠旧键防重。**[Resend 官方幂等契约](https://resend.com/docs/dashboard/emails/idempotency-keys)

作用域也不能忽略：EC2 文档明确说明，在相应区域或可用区作用域之外，相同 ClientToken 可以创建新的实例。[EC2 幂等作用域](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html)

**一个容易误判的做法是：超时后用 `K/A`、`K/B` 生成稳定子键。**  
这只能约束以后使用这些子键的请求。如果第一次提交只携带整批键 K，执行端没有建立 K 与逐项子键的对应关系，这些子键就无法追溯性地保护已经发生的 A。

**3．超时后的“未知状态”决定了能否安全拆批。**

Workflow 应当区分：

- **已确认提交**：保留原身份，不作为新操作重新执行。
- **已确认未执行，且原请求不会再执行该项**：可以重新分批提交。
- **执行结果未知**：使用原契约允许的同键重试、权威状态查询或请求终结机制；不能因为“没有回执”就换键重发。

“查询暂时没查到”也不一定证明未执行，原请求可能仍在运行，或状态尚未可见。

能够返回明确逐项结果的接口更利于恢复。例如 DynamoDB `BatchWriteItem` 会返回 `UnprocessedItems`，官方要求针对这些未处理项重试。不过，这种已收到明确结果的情形，不能直接等同于整个响应丢失的超时情形。[BatchWriteItem 官方说明](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_BatchWriteItem.html)

错误响应的含义也因接口而异：Stripe 当前文档区分 API v1 保存并重放包括 `500` 在内的结果，以及 API v2 尽可能继续失败或部分失败工作的行为。因此，“同键重试会做什么”必须按具体版本核验。[Stripe 官方说明](https://docs.stripe.com/api/idempotent_requests)

**4．“Workflow＋稳定 ID”也有一个必要边界。**

如果只有客户端保存稳定 ID，外部工具既不接受这个 ID，也不能查询执行结果，仍然存在：

```text
外部效果成功 → 客户端尚未记录成功便崩溃 → 恢复后再次调用
```

此时，本地账本不能独自保证外部效果只发生一次。即便使用 Outbox，目标端仍可能收到重复消息，需要目标端防重或等价机制。AWS 的 Outbox 文档明确列出了这一限制。[Transactional Outbox 官方说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

因此，合理的职责分工是：**Agent 提议新的分批、顺序和恢复计划；Workflow 校验它是否保留效果身份、授权绑定、去重作用域及未决请求约束，再决定是否执行。**

对当前课程研究，这给出了一个可检验的具体问题：

> 对内容互异、各授权一次的操作，Agent 超时后拆批，是否从“整请求幂等”跨出了原保护范围？逐项幂等契约能否避免重复，同时减少恢复受阻？

当前模拟器已经按项保存回执，尚不能充分检验整请求键被拆批绕开的情形。本轮结论来自官方契约与代码核查，未调用真实供应商接口验证。
